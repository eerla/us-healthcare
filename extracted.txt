Mapping the U.S. Healthcare System with 
Public Data 
Data-engineering experiment + AI-agent implementation handoff 
Core question: There are millions of healthcare providers and thousands of hospitals. Why can it still be difficult to get an  
appointment, and what does the healthcare system actually look like when modeled as data? 
Primary case study: build the national data model first, then produce a Connecticut-focused analysis as the concrete story. 
The project should be able to expand nationally after the pipeline is proven. 
Recommended stack: Python + DuckDB/Polars for ingestion and profiling, BigQuery for the analytical warehouse, dbt for 
transformations/tests, and a lightweight visualization layer such as Looker Studio, Streamlit, or Observable. The agent may 
choose an equivalent stack if it keeps the same data contracts. 
1. What this experiment is trying to prove 
Do not begin by assuming that appointment difficulty is caused by a simple shortage of doctors. Test competing 
explanations.

7. Canonical transformations 
1. Normalize NPI to a 10-character string. Never cast it to an integer. 
2. Split NPPES Type 1 individuals and Type 2 organizations into separate logical entities.

3. Explode NPPES taxonomy fields into a provider-specialty bridge rather than keeping only one taxonomy. 
4. Explode primary and reference practice locations into a provider-location bridge. 
5. Normalize ZIP to ZIP5 and retain the original raw ZIP field. 
6. Attach county/state using Census geography. Keep a geography_match_method column. 
7. Deduplicate clinician rows at the correct analytical grain; the CMS clinician file is not person -grain. 
8. Use NPI as the cross-source key for provider-level utilization. 
9. Use explicit facility identifiers when available; do not equate facility_name with a unique facility. 
10. Create a source_snapshot_date on every core bridge/fact table. 
11. Maintain row-count and uniqueness tests for every source and transformation. 
12. Create a data_quality table containing source, snapshot, rows_loaded, rows_rejected, null_rate, duplicate_rate, and 
checksum. 
8. SQL analyses — 15 experiments 
The examples below use BigQuery-style SQL. Replace project.dataset names with the actual environment. The agent should 
implement each query as a versioned model or analysis file and save the output used in the article.  
8.1 How many unique NPIs exist by entity type? 
SELECT 
  entity_type_code, 
  COUNT(DISTINCT npi) AS unique_npis 
FROM core.dim_provider 
GROUP BY 1 
ORDER BY unique_npis DESC; 
Story: NPI count is a provider/entity enumeration count, not a count of practicing doctors. 
8.2 How many individual clinicians by specialty? 
SELECT 
  specialty_group, 
  COUNT(DISTINCT provider_sk) AS clinicians 
FROM core.dim_provider_specialty 
WHERE entity_type_code = '1' 
GROUP BY 1 
ORDER BY clinicians DESC; 
8.3 Primary-care supply per 100,000 population 
WITH supply AS ( 
  SELECT state, 
         COUNT(DISTINCT provider_sk) AS providers 
  FROM mart.mart_provider_supply 
  WHERE specialty_group = 'Primary Care' 
  GROUP BY state 
) 
SELECT 
  s.state, 
  s.providers, 
  p.population, 
  SAFE_DIVIDE(s.providers * 100000, p.population) AS providers_per_100k 
FROM supply s 
JOIN mart.state_population p USING (state) 
ORDER BY providers_per_100k DESC;

10. The central Medium narrative 
Suggested title: 'I Tried to Map the U.S. Healthcare System with Public Data. Here’s Why Getting an Appointment Is So Hard.'  
Alternative: 'There Are Millions of Healthcare Providers. So Why Is Getting an Appointment Still So Hard?'  
Opening: start with the contradiction. The public can count millions of NPIs and thousands of hospitals, yet a patient does 
not experience the healthcare system as a national pool of providers. 
Act 1 — Count the doctors. Explain NPI/entity counts and why rows are not people. 
Act 2 — Put them on a map. Show geographic and specialty differences. 
Act 3 — Connect them to groups and hospitals. Reveal the healthcare graph. 
Act 4 — Add Medicare utilization. Show that provider presence and provider capacity are not the same measurement.  
Act 5 — Add insurance network metadata for a selected market/plan. Show the accessible pool shrinking, but only where the 
data supports it.

Conclusion: the useful mental model is not 'How many doctors exist?' It is 'How many appropriate providers are

11. What NOT to claim 
• Do not say NPPES contains the number of licensed doctors. CMS explicitly says NPI issuance does not validate licensure 
or credentialing. 
• Do not count CMS clinician rows as people. The file is at clinician/enrollment/group/address grain.  
• Do not claim Medicare utilization equals total healthcare utilization. It covers Original Medicare fee -for-service Part B 
data. 
• Do not infer that a provider is accepting new patients from an NPI or Medicare enrollment record. 
• Do not infer appointment wait time from utilization alone. 
• Do not assume a hospital name is a unique corporate entity. 
• Do not claim a provider is in-network for a commercial plan unless the provider-plan relationship is actually observed in 
the selected network data. 
• Do not combine datasets from different years without exposing the year mismatch. 
• Do not use patient-level or protected health information. This experiment should use public aggregate/provider/facility 
data only.

ACCEPTANCE CRITERIA 
1. A fresh environment can run the pipeline from documented commands. 
2. Raw files are not modified in place. 
3. All datasets have source metadata. 
4. NPI joins do not create unexplained many-to-many explosions. 
5. Provider counts distinguish unique NPI from CMS clinician rows. 
6. Connecticut can be selected through configuration rather than hard-coded SQL. 
7. Every chart is generated from a versioned query/output. 
8. Every published claim can be traced to a dataset, snapshot, and SQL model. 
9. The final README explains known limitations. 
10. The agent must stop and ask for human review when a required relationship cannot be supported by a public 
identifier. 
 
DO NOT 
- invent appointment wait times 
- invent insurance network participation 
- claim that NPI = licensed doctor 
- claim Medicare utilization = all utilization 
- silently deduplicate source records 
- silently mix years 
- publish personal or patient-level information

17. Recommended first build 
Do not download every possible healthcare dataset on day one. Build the smallest end-to-end slice first: 
13. Download the current NPPES V2 monthly file and reference files. 
14. Filter to Connecticut for the first analytical run after raw preservation, while retaining the national raw source if storage  
permits. 
15. Build unique NPI/provider and provider-location dimensions. 
16. Load the CMS Doctors & Clinicians National Downloadable File and Facility Affiliation Data. 
17. Load CMS Hospital General Information. 
18. Load Census population/geography. 
19. Produce provider density, specialty density, clinician-row-vs-NPI, provider-to-facility, and facility concentration 
analyses. 
20. Only after those are stable, add Medicare utilization. 
21. Then add Marketplace plan/network metadata. 
22. Finally decide whether a selected-plan provider-level network match is strong enough to publish. 
The first milestone should be a single reproducible chart: 'The healthcare provider funnel in Connecticut.' If that chart is 
analytically sound, the rest of the project has a strong foundation.
